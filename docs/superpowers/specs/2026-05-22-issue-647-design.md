# Issue 647 Design: Add paged customer directory list API and route empty search to list

## Summary

Issue #647 adds a dedicated paged browse API for Customer Directory on the CRM accounts surface while keeping criteria search as a separate concern. The backend in this repository will expose a new browse endpoint, keep the existing search endpoint, reuse one shared response schema, and distinguish browse vs. search in event logging and OpenAPI. A coordinated frontend change in another repository will route empty query input to browse and non-empty query input to search.

## Goals

- Make Customer Directory load normally when opened with no query.
- Provide a dedicated paged browse endpoint with explicit paging and sorting semantics.
- Keep criteria-based search available and unchanged in purpose.
- Reuse one response schema for browse and search so frontend mapping stays simple.
- Ensure empty-result success responses are represented as normal JSON, not failure shapes.
- Keep authorization aligned with current CRM party view access.
- Distinguish browse and search operations in observability.

## Non-Goals

- Redesign the Customer Directory UI.
- Introduce advanced filtering beyond page, size, and sort for browse.
- Change tenant or org-level data-scope policy.
- Replace the existing POST search endpoint.
- Implement frontend changes in this repository.

## Current State

The repository already exposes:

- `POST /v1/crm/accounts/parties/search` in `CrmAccountsController`
- a `SearchPartiesRequest` / `SearchPartiesResponse` DTO pair
- a `PartyService.searchParties(...)` implementation
- an older generic paged customer GET surface under `CustomerController`

The current search implementation uses search-oriented DTOs and does not provide a dedicated browse contract on the CRM accounts surface. The older generic customer controller lives on a different surface and returns a different response type, so it is not a clean fit for Customer Directory browse behavior.

## Proposed API Design

### New browse endpoint

Add a new endpoint:

- `GET /v1/crm/accounts/parties`

Behavior:

- Used for browse semantics only
- Accepts `page`, `size`, and `sort` query parameters
- Requires `crm:party:view`
- Returns the existing shared response schema used by search

### Existing search endpoint

Keep:

- `POST /v1/crm/accounts/parties/search`

Behavior:

- Used only for criteria-based search
- Continues to accept `SearchPartiesRequest`
- Continues to return `SearchPartiesResponse`
- No longer serves as the intended browse contract for empty query behavior

## Shared Response Contract

Browse and search will both return the same response shape so the frontend can use one mapping path. The current response DTO should remain the shared response contract for this issue unless a later cleanup renames it without changing wire format.

Required contract properties:

- `results`: array of party summaries
- `totalCount`: total matching records
- `pageNumber`: current zero-based page number
- `pageSize`: current page size

For success cases:

- responses must always be valid JSON
- zero results must return `200` with `results: []`
- paging metadata must still be present for empty results

## Backend Design

### Controller

Extend `CrmAccountsController` with a dedicated GET browse handler for `/parties`.

The controller will:

- accept pageable query parameters
- normalize defaults through Spring paging configuration or explicit service normalization
- delegate to a dedicated browse method on `PartyService`
- return `ResponseEntity<SearchPartiesResponse>`
- emit a dedicated browse event ID

### Service

Extend `PartyService` with a browse-specific method separate from `searchParties`.

The browse service will:

- accept pageable input
- normalize absent or incomplete page, size, and sort values
- use repository-backed pageable retrieval rather than criteria search semantics
- map results into the existing `SearchPartiesResponse.PartySummary`
- return a fully populated `SearchPartiesResponse`

The search service remains separate and criteria-driven.

### Repository

Use repository pageable retrieval for browse with deterministic ordering.

Browse should support:

- explicit requested sort when allowed
- a stable fallback sort when none is provided

The fallback sort must be deterministic so page-to-page navigation is stable.

## Default Behavior

Recommended defaults for browse:

- `page = 0`
- `size = 20`
- deterministic fallback sort when `sort` is absent

These defaults should be documented in OpenAPI and enforced consistently in controller and service behavior.

## Authorization

The new browse endpoint will require the same permission policy as the current party search endpoint:

- `crm:party:view`

No authorization broadening is included in this issue.

## Observability

Browse and search must be distinguishable in emitted events.

Changes:

- keep existing `CUSTOMER_PARTY_SEARCH` for POST search
- add a new event type for browse, for example `CUSTOMER_PARTY_BROWSE`
- register the new event type in `EventTypes`

This preserves action-level latency and error visibility for customer directory behavior.

## OpenAPI Changes

Update `pos-customer/openapi.yaml` to:

- add `GET /v1/crm/accounts/parties`
- document `page`, `size`, and `sort` query parameters
- document the shared response schema for browse
- preserve the existing POST search operation

The aggregate gateway spec should continue to reflect the customer module changes through the repository’s existing OpenAPI validation flow.

## Coordinated Frontend Contract

This repository will not implement the frontend change, but the backend contract is designed for a coordinated frontend rollout.

Frontend behavior expected by this design:

- trimmed empty query -> call `GET /v1/crm/accounts/parties`
- non-empty query -> call `POST /v1/crm/accounts/parties/search`
- both responses map through one shared result model
- empty results render as a normal empty state, not a failure state

## Error Handling

Browse-specific rules:

- invalid paging parameters should produce normal Spring validation or request parsing errors
- empty browse result is not an error
- browse success must not return an empty-body `200`

Search-specific rules remain separate from browse. This issue does not require redefining all existing search validation rules, only ensuring the browse path is explicit and success-shaped.

## Testing Strategy

### Controller tests

Add or extend tests for:

- `GET /v1/crm/accounts/parties` returns `200` with paging metadata
- default browse request uses expected defaults
- explicit paging and sort parameters are honored
- empty browse results return `200` with empty `results`
- unauthorized browse requests return `403`

### Service tests

Add or extend tests for:

- browse normalization of default page, size, and sort
- browse mapping into the shared response DTO
- deterministic ordering behavior
- empty browse result shape

### OpenAPI / contract tests

Validate:

- new browse path exists in module OpenAPI
- parameters and response schema are documented correctly
- aggregate OpenAPI remains valid

### Event registration coverage

Validate:

- new browse event type is registered
- browse and search do not share the same event ID

## Implementation Notes

- Keep browse and search methods separate in the service API.
- Do not route the new browse behavior through the older generic `CustomerController`.
- Reuse the existing shared response schema to minimize frontend integration cost.
- Prefer narrow, targeted changes to `CrmAccountsController`, `PartyService`, `PartyServiceImpl`, OpenAPI, and associated tests.

## Risks and Mitigations

### Risk: browse and search drift apart in response shape

Mitigation:

- use one shared response DTO
- cover both paths with controller and contract tests

### Risk: unstable ordering causes page churn

Mitigation:

- define and test a deterministic fallback sort

### Risk: frontend still calls POST search for empty query

Mitigation:

- document the coordinated contract clearly
- keep backend browse endpoint explicit and discoverable in OpenAPI

## Acceptance Criteria

- A new paged browse endpoint exists on the CRM accounts API surface.
- Browse uses GET semantics and documented page/size/sort parameters.
- Browse and search return the same response schema.
- Empty browse results return `200` with valid JSON and paging metadata.
- Browse authorization matches current CRM party view authorization.
- Browse and search emit distinct event types.
- OpenAPI documents the new browse path and remains valid.
- The backend contract clearly supports frontend routing of empty query to browse and non-empty query to search.
