# Tenancy schema conventions (ADR-0062)

Every persisting module's Flyway history was flattened on 2026-09-09 into a single baseline with
the ADR-0062 row-level multitenancy schema folded in. This page is the contract the baselines
follow and the checklist for adding a table. The decision record is
`durion/docs/adr/0062-postgres-row-level-multitenancy.adr.md`; the workstreams are in
`durion/docs/architecture/plans/adr-0023-suppression-postgres-multitenancy-plan.md`.

## Layout of a module's migrations

| File | What it holds |
| --- | --- |
| `V1__baseline_<module>.sql` | The whole schema as of the flatten, with tenancy. Generated by `scripts/db/tenancy/flatten.py`; edit it by hand from now on (add tables, columns, constraints) rather than adding `V2__...` files while the platform is in alpha and databases are recreated between builds. |
| `V2__seed_<module>.sql` | Rows the retired versioned scripts inserted (reference and bootstrap data), only where there were any. |
| `V2__timescaledb_emitted_event.sql` (pos-event-receiver only) | The hypertable, compression and continuous aggregate; needs the `timescaledb` extension of the Compose image, so it is kept out of the portable baseline. |
| `R__seed_*.sql` | Repeatable seeds, unchanged in content; each now opens with the tenant binding below and its `ON CONFLICT` targets lead with `tenant_id`. |
| `../tenancy-global-tables.txt` | The module's global tables with a reason each. Everything else is tenant-scoped. |

`pos-mcp-server` still carries a parallel `db/h2-migration` set for its H2 `dev`/`test` profiles,
and `pos-supplier` carries one (its retired chain, verbatim) for the H2 test slices that validate
the entities against real DDL and prove its unique, check and foreign-key constraints. Neither set
was flattened; both go away when those modules move to Testcontainers (plan WS5).
`pos-inquiry` has no Flyway migrations (Hibernate `ddl-auto: update`) and is outside this contract.

## What every tenant-scoped table has

```sql
tenant_id uuid DEFAULT public.app_current_tenant() NOT NULL          -- first column
ALTER TABLE t ENABLE ROW LEVEL SECURITY;
ALTER TABLE t FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON t
    USING (tenant_id = public.app_current_tenant())
    WITH CHECK (tenant_id = public.app_current_tenant());
CREATE INDEX t_tenant_idx ON t (tenant_id);                          -- unless an index already leads with it
ALTER TABLE t ADD CONSTRAINT t_tenant_key UNIQUE (tenant_id, <pk>); -- the composite FK target
```

- `app_current_tenant()` is `NULLIF(current_setting('app.current_tenant', true), '')::uuid`,
  defined once per database at the top of the baseline. Unbound, it is NULL: the policy hides every
  row and the `NOT NULL` default refuses every insert. Fail closed.
- Every `UNIQUE` constraint, unique index and `EXCLUDE` constraint leads with `tenant_id`, so a
  business key is unique within a tenant, not across the platform. An `INSERT ... ON CONFLICT (cols)`
  against such a table must name `(tenant_id, cols)`; `ON CONFLICT DO NOTHING` and
  `ON CONFLICT ON CONSTRAINT name` are unaffected.
- Every foreign key from a scoped table to a scoped table is composite:
  `FOREIGN KEY (tenant_id, x) REFERENCES y (tenant_id, id)`. Foreign-key checks run with the
  owner's privileges and bypass RLS, so a single-column key could be satisfied by another tenant's
  row. Keys to global tables stay single-column.
- Primary keys are unchanged (UUID v7, globally unique).

Global tables (`tenancy-global-tables.txt`) carry none of this. The recorded classes: transactional
outboxes and processed-event ledgers (they carry `tenant_id` as plain data), Spring Batch metadata,
the event-type registry, the permission catalog, the MCP tool/screen/prompt catalogs and RAG
corpus, and the vehicle reference and fitment modules in full.

## Binding the tenant (transitional until plan WS1)

Nothing in the application binds `app.current_tenant` yet; `pos-tenancy-common` (WS1) adds the
`TenantAwareDataSource` that sets it per checkout from the request's `X-Tenant-Id`. Until then:

| Where | Binding |
| --- | --- |
| Compose and alpha | `postgres/init-tenancy.sh` sets `ALTER ROLE "$POSTGRES_USER" SET app.current_tenant = '<alpha default tenant>'`; every service still connects as that role, so every connection is bound. WS1 removes that line and switches services to `pos_app`. |
| Flyway seeds | Each seed file opens with `SELECT set_config('app.current_tenant', '<alpha default tenant>', true)`, transaction-local to the migration. |
| Testcontainers tests (`pg` profiles) | `spring.datasource.hikari.connection-init-sql` sets the same value per connection. Tests that open raw JDBC connections set it themselves. |
| H2 `dev`/`test` profiles and `@DataJpaTest` slices | Hibernate `create-drop` from the entities; no tenancy columns, no Flyway (`spring.flyway.enabled: false` in every `application-dev.yml`, and inline in the slices that used to validate against the old H2-compatible baselines). The baseline is Postgres-only. |

Constants:

| Constant | Value | Meaning |
| --- | --- | --- |
| alpha default tenant | `01900000-0000-7000-8000-000000000001` | The one tenant the alpha cell serves until `pos-tenant` (plan WS2a) provisions tenants. Every seed row and every transitional binding uses it. |
| platform tenant | `01900000-0000-7000-8000-000000000000` | Reserved for the platform-operator tenant of ADR-0062 §7; created by the `pos-tenant` bootstrap migration, not used yet. |

`postgres/init-tenancy.sh` also creates the shared `pos_app` role (LOGIN, `NOSUPERUSER`,
`NOBYPASSRLS`, DML and sequence usage on every `pos_*` database, default privileges for tables
created later). Services do not use it until WS1.

## Adding a table

1. Add it to `V1__baseline_<module>.sql` with `tenant_id` first, the policy block, the tenant
   index and the `(tenant_id, <pk>)` key, following any existing table in the file.
2. Lead every unique constraint and unique index with `tenant_id`; make foreign keys to scoped
   tables composite.
3. If the table is global, list it in `tenancy-global-tables.txt` with a reason and skip the above.
4. The entity needs no `tenant_id` mapping until `TenantScopedEntity` exists (WS1); Hibernate's
   `validate` ignores unmapped columns and the column default fills the value.

## What the retrofit changed for application code

- `INSERT ... ON CONFLICT (cols)` on a scoped table needs `(tenant_id, cols)`. The only
  column-targeted form in application code today is on a global table (`mcp_tool`); the repeatable
  seeds were rewritten by `scripts/db/tenancy/rescope_conflicts.py`.
- Entities that already carried a `tenant_id` column (`pos-people`: `time_period`,
  `timekeeping_entry`) keep their mapping; the column gained the default.
- Tests that ran retired versioned scripts verbatim or proved historical backfills were removed
  (pos-inventory putaway/storage-compatibility migration tests, pos-location storage-location
  capability test, pos-accounting event-reference and period backfill ITs). The seed-content guards
  in pos-accounting and pos-security-service now read the flattened seeds.
