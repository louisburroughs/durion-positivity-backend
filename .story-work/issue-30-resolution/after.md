## Story Intent
**As an** Inventory Manager,
**I want** the system to automatically generate replenishment tasks for primary picking locations when their stock levels fall below a defined minimum,
**so that** we can proactively move inventory from backstock to ensure parts are always available for mechanics, minimizing order fulfillment delays and preventing stockouts at the point of work.

## Actors & Stakeholders
- **Primary Actor:**
  - **Inventory Service (System):** The automated process responsible for monitoring stock levels and creating replenishment tasks.
- **Key Stakeholders:**
  - **Inventory Manager:** Oversees inventory health and relies on this process to maintain optimal stock levels in picking locations.
  - **Warehouse Associate:** Executes the replenishment tasks generated by the system.
  - **Mechanic / Service Technician:** The end consumer who benefits from consistently stocked pick faces, enabling faster job completion.

## Preconditions
1.  A clear distinction between "Pick Face" (primary picking) and "Backstock" (overflow/storage) location types exists within the system.
2.  `ReplenishmentPolicy` records exist and are associated with specific Item-Location pairs, defining their `minimumQuantity` and `maximumQuantity` thresholds.
3.  The inventory system has real-time, accurate quantity-on-hand data for all items in all defined locations.
4.  The functionality to create and persist a `ReplenishmentPolicy` is already implemented or will be completed as a prerequisite.

## Functional Behavior
The system shall provide an automated mechanism to generate inventory replenishment tasks.

### Trigger (Hybrid Model)

**Primary Trigger — Event-Driven (Required)**
- The system listens for `InventoryDecremented` events.
- A replenishment check is triggered **only when**:
  - The decrement occurs in a **Pick Face** location (`isPickFace = true`), **AND**
  - The resulting `onHandQuantity` falls **at or below** the `minimumQuantity` threshold for that pick face (`onHandQty <= minQty`).
- **Debouncing:** To control system load, checks are debounced per `(productId, pickFaceLocationId)` pair (e.g., maximum once every 60 seconds).

**Secondary Trigger — Batch Job (Required Safety Net)**
- A scheduled batch process runs every **5–15 minutes** to scan all pick faces for items below their minimum thresholds.
- This safety net ensures:
  - Missed events are caught
  - Recovery from transient failures
  - Reconciliation after bulk inventory adjustments

**Rationale:** The hybrid approach balances responsiveness (event-driven) with reliability (batch safety net), following standard patterns for inventory correctness.

### Process
1.  The system identifies an item in a Pick Face location where the `currentQuantityOnHand` has dropped below the `minimumQuantity` specified in its `ReplenishmentPolicy`.
2.  Upon detection, the system calculates the required replenishment quantity: `quantityToMove = maximumQuantity - currentQuantityOnHand`.
3.  The system queries for available stock of the same item in "Backstock" locations using the **Backstock Sourcing Logic** (see below).
4.  If sufficient backstock is found, the system creates a `ReplenishmentTask` with a `PENDING` status.
5.  The task must contain all necessary information for a warehouse associate to execute the move:
    -   `itemSKU`
    -   `quantityToMove`
    -   `sourceLocationId` (the identified backstock location)
    -   `destinationLocationId` (the pick face location needing replenishment)
    -   `triggerType` (`EVENT` or `BATCH`)
    -   `decisionReason` (`BELOW_MIN` or `SAFETY_SCAN`)
    -   `createdAt` timestamp

### Backstock Sourcing Logic (Deterministic Hierarchy)

When multiple backstock locations contain the same item, the system selects the source location using the following **deterministic hierarchy**:

1.  **FEFO/FIFO Compliance (if applicable)**
    -   If the item is lot-controlled or expiry-controlled:
        -   Choose the backstock location with the **earliest expiry date** (FEFO)
        -   If no expiry data, use **earliest receipt date** (FIFO)
2.  **Sufficient Quantity**
    -   Prefer a **single backstock location** that can fully satisfy the `quantityToMove`
3.  **Location Proximity (optional enhancement)**
    -   If location topology data exists, prefer the location with the lowest layout order (Zone → Aisle → Rack → Bin)
4.  **Highest On-Hand Quantity**
    -   Final deterministic tie-breaker: select the location with the most available stock

**Note on "Any Location":** While "any location with sufficient quantity" can serve as a last-resort tie-breaker, it is **not** the primary rule. The deterministic hierarchy above ensures predictable, auditable behavior while maintaining FEFO/FIFO compliance and simplifying audit trails.

### Partial Replenishment
- If no single backstock location has sufficient quantity to reach `maximumQuantity`:
  - The system creates **multiple `ReplenishmentTask` records**, one for each backstock location
  - Tasks are ordered following the same sourcing hierarchy
  - The sum of all task quantities should bring the pick face to (or as close as possible to) `maximumQuantity`

### Idempotency
- Replenishment tasks must be **idempotent** per `(productId, pickFaceLocationId, thresholdCrossing)` tuple
- The system prevents duplicate task creation for the same replenishment trigger
- If a `PENDING` or `IN_PROGRESS` task already exists for the same item-location pair, no new task is created

## Alternate / Error Flows
- **Insufficient Backstock:** If the total available quantity in all backstock locations is less than the calculated `quantityToMove`, the system shall create `ReplenishmentTask`(s) for the entire available backstock quantity.
- **No Backstock:** If there is zero available quantity of the item in any backstock location, no `ReplenishmentTask` is created. This event should be logged as a potential supply chain issue and recorded in metrics.
- **Existing Open Task:** If a `PENDING` or `IN_PROGRESS` `ReplenishmentTask` already exists for the same item and destination location, the system shall not create a duplicate task.
- **Invalid Policy:** If a `ReplenishmentPolicy` is found where `minimumQuantity >= maximumQuantity`, the system shall log a configuration error and ignore that policy during the evaluation.

## Business Rules
- A replenishment task is only triggered when `currentQuantityOnHand` is strictly less than `minimumQuantity`.
- The target fill quantity for a replenishment is always the `maximumQuantity` defined in the policy.
- The system must prevent the creation of duplicate, open replenishment tasks for the same item-location pair.
- All replenishment decisions must follow the deterministic backstock sourcing hierarchy.
- Event-driven triggers must be debounced to control system load.

## Audit & Observability
- **Audit Log:** The creation of every `ReplenishmentTask` must be recorded in an immutable audit log, including:
  - The state of the inventory and policy that triggered it
  - The `triggerType` (`EVENT` or `BATCH`)
  - The `decisionReason` (`BELOW_MIN` or `SAFETY_SCAN`)
  - The sourcing hierarchy decisions made
  - Timestamp (`occurredAt`)
  - Source backstock location(s) selected and reasoning
- **Events:** A `ReplenishmentTaskCreated` event must be published to a message bus (e.g., Kafka, RabbitMQ) upon successful task creation. The event payload should contain all task details including trigger metadata.
- **Metrics:** The Inventory service should expose metrics for monitoring:
  - `replenishment_tasks.created.count` (counter, tagged by location/item/triggerType)
  - `replenishment_evaluation.duration.ms` (timer, tagged by triggerType)
  - `replenishment_backstock.unavailable.count` (counter for when no backstock is found)
  - `replenishment_event.debounced.count` (counter for debounced events)
  - `replenishment_batch.scan.count` (counter for batch scan executions)

## Design Decisions (Resolved from Clarification #228)

### Decision 1: Triggering Mechanism
**Question:** What is the precise trigger for the replenishment check?

**Answer:** **Hybrid Model** — Event-Driven primary trigger + Batch job safety net.

**Primary Trigger:** Event-driven on `InventoryDecremented` events when:
- Decrement occurs in a Pick Face location
- Resulting on-hand quantity falls at or below minimum threshold
- Debounced per `(productId, pickFaceLocationId)` (e.g., once every 60 seconds)

**Secondary Trigger:** Scheduled batch scan every 5–15 minutes to catch missed events, recover from failures, and reconcile bulk adjustments.

**Rationale:** Event-driven alone risks missed replenishment due to transient failures. Batch alone introduces unacceptable latency. Hybrid is the standard pattern for inventory correctness, balancing responsiveness with reliability.

### Decision 2: Backstock Sourcing Logic
**Question:** If an item exists in multiple backstock locations, what logic determines the source?

**Answer:** **Deterministic Hierarchy** (not "any location").

**Sourcing Order:**
1. FEFO/FIFO compliance (earliest expiry or receipt date)
2. Sufficient quantity (prefer single location fulfilling full need)
3. Location proximity (optional, if topology data exists)
4. Highest on-hand quantity (final tie-breaker)

**Clarification on "Any Location":** While "any location with sufficient quantity" can serve as a last-resort tie-breaker, it is NOT the primary rule. The deterministic hierarchy ensures:
- FEFO/FIFO compliance
- Predictable, auditable behavior
- Simplified audit and replay

### Decision 3: Additional Behaviors
**Partial Replenishment:** If no single backstock location has sufficient quantity, create multiple putaway tasks ordered by the same sourcing logic.

**Idempotency:** Tasks must be idempotent per `(productId, pickFaceLocationId, thresholdCrossing)`.

**Audit Requirements:** Each decision must record `triggerType`, `sourceBackstockLocationId(s)`, `decisionReason`, and `occurredAt`.
